## 1. Cloudflare D1

У Cloudflare створіть D1 базу, наприклад `oracle-portal`. Застосуйте чотири схеми в зазначеному порядку:

`worker/migrations/0001_oracle_portal.sql`, `worker/migrations/0002_contacts.sql`, `worker/migrations/0003_public_counters.sql` та `worker/migrations/0004_collaboration_chat.sql`

Через Wrangler, після входу в потрібний акаунт Cloudflare:

```bash
npx wrangler d1 execute oracle-portal --remote --file=worker/migrations/0001_oracle_portal.sql
npx wrangler d1 execute oracle-portal --remote --file=worker/migrations/0002_contacts.sql
npx wrangler d1 execute oracle-portal --remote --file=worker/migrations/0003_public_counters.sql
npx wrangler d1 execute oracle-portal --remote --file=worker/migrations/0004_collaboration_chat.sql
```

Або виконайте SQL зі схеми у D1 SQL-консолі. Після створення бази підключіть її до **наявного** Cloudflare Worker під точною назвою binding **`DB`** (Workers → ваш Worker → Settings → Bindings → D1).

Перевірте, що створені таблиці `guest_trials`, `users`, `login_challenges`, `user_sessions`, `user_daily_usage`, `oracle_questions`, `portal_events`, `contact_requests`, `public_page_stats`, `public_unique_browsers`, `public_page_unique_browsers`, `collaboration_threads`, `collaboration_messages`.

## Подвійний публічний лічильник

На кожній із трьох сторінок показуються **Загалом переглядів** і **Унікальні браузери**. Перемикач **Ця сторінка / Увесь сайт** відображає або статистику поточної сторінки, або підсумок усіх трьох сторінок. До підключення D1 і нового Worker інтерфейс показує знак «—», а не вигаданий нуль.

Додатково до D1 і міграції `0003_public_counters.sql` встановіть у Cloudflare Worker окремий секрет `VISITOR_HASH_KEY` (щонайменше 32 випадкові символи). Секрет не передається браузеру й не розміщується в GitHub. Не змінюйте його без причини: після ротації давні браузери можуть порахуватися повторно як нові.

Браузер створює випадковий ідентифікатор у `localStorage`, сервер зберігає тільки HMAC-відбиток. **Унікальний браузер — це не гарантовано унікальна людина.** Перегляди рахуються за фактом зафіксованого завантаження сторінки. Показники починаються з активації цієї функції і не відновлюють історичні відвідування. За заборони локального сховища перегляд може не потрапити до лічильника.

Перевірки: `GET /access/counters?page=model` повертає `site.total_views`, `site.unique_browsers`, `current_page.total_views`, `current_page.unique_browsers`. Після першого перегляду «унікальні браузери» збільшуються на 1; повторне відкриття тієї ж сторінки в тому самому браузері збільшує лише «загалом». Перехід на іншу сторінку не повинен удруге збільшувати загальну кількість унікальних браузерів сайту.

**Не використовуйте лічильник як верифікований реєстр фізичних осіб:** його значення можуть спотворювати боти, спільні браузери, очищення даних і штучні запити. Для захисту публічного `POST /access/pageview` рекомендується Cloudflare WAF / Rate Limiting. Перевірте правову основу для використання постійного ідентифікатора у браузері та за потреби додайте механізм отримання згоди.

## 2. Cloudflare Turnstile — гостьова сесія

Створіть Turnstile widget для hostname `andrew-hvc.github.io`. Додайте у налаштування Worker:

- `TURNSTILE_SITE_KEY` — відкритий ключ сайту (звичайна змінна).
- `TURNSTILE_SECRET` — **секрет**, тільки в Cloudflare Worker Secrets.

Без обох параметрів гостьовий доступ недоступний. **Перевірка токена відбувається на сервері** через Siteverify.

Одна гостьова сесія дає максимум **5 запитань**. Гостьовий браузер зберігає випадковий ключ у localStorage; D1 зберігає його криптографічний відбиток і витрати запитань. Це **обмеження для браузерного профілю**, а не гарантоване «один раз на фізичну людину». Для протидії масовому створенню нових профілів налаштуйте також Cloudflare WAF / Rate Limiting на `/access/guest`, `/access/email/start`, `/access/contact` та POST до Оракула.

## 3. Реєстрація через пошту

У поточному варіанті одноразові коди надсилаються через Resend API. Потрібні:

- `RESEND_API_KEY` — секрет, виданий Resend.
- `RESEND_FROM` — перевірена адреса відправника (на перевіреному домені).
- `OTP_PEPPER` — додатковий випадковий секрет, не менше 32 символів.

Без цих налаштувань **реєстрація не буде активною**. Поштове підтвердження діє 10 хвилин, до 5 невдалих спроб; є обмеження повторних запитів коду. Паролі користувачів не зберігаються.

Для зареєстрованих користувачів початковий ліміт — **30 запитань/добу**; можна змінити Worker variable `MEMBER_DAILY_QUOTA` (кількість). Сервер рахує використання у D1, а не в JS. Ліміт скидається за календарною добою UTC.

## 4. Закритий адміністративний кабінет

Додайте секрет `ADMIN_DASHBOARD_TOKEN`, випадковий рядок **понад 32 символи**. Він має бути **іншим**, ніж `ORACLE_TEST_TOKEN`. Ні в якому разі не розміщуйте ці секрети у GitHub, JavaScript сторінок, URL чи метаданих.

Відкрийте `admin.html`, введіть `ADMIN_DASHBOARD_TOKEN`. Ключ утримується **тільки в пам'яті відкритої вкладки**, не записується у localStorage або sessionStorage.

Кабінет отримує з API:
- огляд за 30 днів (запитання, сесії з питаннями, гості, зареєстровані, перегляди, обсяги API, оцінки, звернення);
- теми й початкові сторінки;
- журнал звернень із текстами **лише за згодою**;
- CSV для адміністративного експорту;
- захищена скринька повідомлень про співпрацю та їхні статуси;
- порівняння тематичних груп Google ↔ Оракул;
- звіт ШІ за агрегованими даними й дозволеними до аналізу текстами.

Орієнтовна вартість API може відображатися, якщо вручну задати `MODEL_INPUT_USD_PER_M` і `MODEL_OUTPUT_USD_PER_M` (USD за мільйон токенів **саме обраної моделі**). Ці оцінки **не замінюють** реальні витрати з OpenAI Billing і можуть не включати пошук та інші платні інструменти.

## 5. Google Search Console

Для порівняння з органічним пошуком є **два шляхи**:

**Без додаткових ключів:** відкрийте у Search Console звіт про ефективність, експортуйте CSV з пошуковими запитами, у кабінеті відкрийте «Пошуковий попит» → виберіть CSV. Він аналізується **локально в браузері**, без завантаження на Worker.

**Автоматичний імпорт:** перевірте ресурс сайту в Google Search Console, увімкніть Search Console API в Google Cloud, створіть Service Account та надайте його email доступ до Search Console property. У Cloudflare Worker задайте:

- `GSC_SERVICE_ACCOUNT_JSON` — **секрет** із повним JSON сервісного облікового запису, без публікації у GitHub.
- `GSC_SITE_URL` — точний ідентифікатор перевіреної властивості Search Console (наприклад, `https://andrew-hvc.github.io/author-resource/`; якщо використано іншу property, вкажіть її дослівно).

Після цього кнопка «Отримати дані Search Console» отримає топ пошукових фраз, сторінки, покази та переходи. Google **не повертає всі запити**; зіставлення з Оракулом є тематичним, а не кореляцією на рівні окремих людей. **Не стверджувати**, що ми знаємо, який саме запит Google належить конкретному відвідувачу Оракула.

## 6. Розгортання Worker

У цьому репозиторії готове джерело **одного Worker**:
`worker/oracle-worker.js`.

У нього вже вбудовано нові маршрути доступу й аналітики — окремий імпорт не потрібен. Він зберігає чинну логіку відповідей Моделі.

Порядок:
1. Створити D1, застосувати міграцію та під'єднати `DB`.
2. Додати потрібні секрети й змінні, не зачіпаючи чинні `OPENAI_API_KEY`, `ORACLE_VECTOR_STORE_ID`, `ORACLE_TEST_TOKEN`.
3. Замінити код наявного Cloudflare Worker кодом `worker/oracle-worker.js` і натиснути Deploy.
   **Поведінка тестового пароля:** коли D1 підключена, старий `ORACLE_TEST_TOKEN` більше не дає доступу за замовчуванням. Для тимчасового адміністративного тестування можна явно встановити `ALLOW_LEGACY_TEST_MODE=true`; перед публічним запуском вимкніть цей прапорець, щоб старий спільний пароль не обходив ліміти.
4. Налаштувати тригер `Cron` `0 3 * * *` для гарантованого автоматичного видалення текстів старше 30 днів (також очищення запускається під час звернень адміністратора).
5. Підтвердити у браузері `GET https://oracle-api.andrewdonenko.workers.dev/access/config`, що `db_enabled`, `guest_enabled`, `member_enabled` відповідають налаштованим службам.

**До кроку 3 сайт показуватиме новий інтерфейс, але гостьова реєстрація та аналітика не запрацюють.** Не намагайтеся замінити це перевіркою квоти лише на фронтенді.

## 7. Контрольні тести

- Без адміністративного ключа `/admin/overview` повертає 401.
- Гостьовий доступ потребує Turnstile, п'ять успішних запитань зменшують ліміт до нуля; шосте повертає 429.
- В іншій вкладці того самого браузера гостьова квота не відновлюється.
- Email-код працює тільки після налаштування Resend; прострочений і неправильний код відхиляються.
- Питання без прапорця згоди зберігається як метадані, без тексту.
- Після згоди текст тимчасово видно в кабінеті; через 30 днів він очищується. Користувач може видалити його раніше.
- Відповідь можна оцінити «Так / Ні» без зміни змісту Моделі.
- Нова форма співпраці переводить відвідувача у `messages.html`, зберігає чернетку лише в `sessionStorage` і не надсилає її до підтвердження email та окремої згоди. Старі анонімні звернення не прив'язуються до акаунтів автоматично.
- ШІ-звіт не публікує інформацію та відокремлює дані від авторських положень.
- Після підключення Google або CSV-імпорту видно тематичне зіставлення без прив'язки Google-запитів до осіб.

## Важливі обмеження

1. **Анонімність автора.** Наявна технічна адреса Worker `oracle-api.andrewdonenko.workers.dev` містить фрагмент особистого імені в домені. Попри відсутність імені в публічному тексті й метаданих сайту, ця адреса видима у браузерних запитах. Щоб усунути таке розкриття, створіть нейтральний домен/маршрут для Worker і оновіть усі виклики API та CSP сайту до публічного запуску.
2. **Приватний кабінет.** GitHub Pages — статичний хостинг: адресу `admin.html` технічно можна відкрити кожному. Конфіденційними залишаються тільки дані API, до яких потрібен серверний секрет. Для додаткового захисту надалі можна розмістити сам кабінет за Cloudflare Access.
3. **Внески.** Оплата API через внески відвідувачів та публічний список спонсорів поки залишаються елементами майбутнього механізму; платіжний канал не підключено й не можна показувати вигаданих спонсорів.
4. **Приватні звернення.** Нова форма на тематичних сторінках готує чернетку й переводить у особистий чат. Перед першим надсиланням користувач підтверджує email одноразовим кодом, після чого створюється розмова в D1. Старі записи `contact_requests` — окремий архів, їх не можна приєднувати до акаунтів лише за неперевіреним email. Пошта відвідувача не використовується для звичайних відповідей у чаті; їхній статус відображається безпосередньо на сайті.
5. **Персональні дані.** Перед відкритим запуском перевірте належне оформлення приватності, контакту контролера даних, політики згоди та договірних/юридичних вимог згідно з місцем експлуатації.

## Приватний чат і сповіщення про звернення

**Архітектура:** `messages.html` і `assets/messages.js` використовують ті самі акаунти, email OTP та секрети сесії, що й Оракул. Потрібне виконання `0004_collaboration_chat.sql`. Тільки користувач із валідним токеном `user_sessions` може створити діалог, надіслати повідомлення або прочитати власні відповіді. Кожна операція перевіряє `user_id` **на сервері**; передавати довільний email недостатньо. Адміністратор має окремі захищені маршрути за `ADMIN_DASHBOARD_TOKEN`.

**Сценарій відвідувача:** на сторінці «Модель», «Фенікс» або «Демомодель» відвідувач заповнює звернення, погоджується на переписку й натискає «Продовжити в чаті». Чернетка на поточній вкладці тимчасово зберігається у `sessionStorage` на 2 години. Після входу через email її можна перевірити й відправити. При успішній відправці формується `collaboration_threads` та перше `collaboration_messages`. Надалі нові повідомлення з боку адміністратора відмічаються непрочитаними; позначку видно біля «Повідомлення» на тематичних сторінках та в Оракулі, **тільки якщо поточна вкладка авторизована**. Нові відповіді перевіряються при поверненні на вкладку й приблизно раз на 30 секунд під час її активності. Це не WebSocket і не миттєве push-сповіщення поза відкритим сайтом.

**Сценарій адміністратора:** вкладка «Діалоги» у `admin.html` містить особисті звернення користувачів, листування, статус «Відкрито/Закрито», кнопку відповіді та позначки нових повідомлень. Вкладка «Звернення» залишена лише для старих непідтверджених звернень, де немає перевіреної належності акаунту.

**Email-сповіщення адміністратору:** додайте окремий секрет `ADMIN_NOTIFY_EMAIL` із вашою приватною адресою у Cloudflare Worker Secrets. Використовуються вже наявні `RESEND_API_KEY` та `RESEND_FROM`; після надходження звернення або нового повідомлення Worker відправляє короткий лист з посиланням на закритий кабінет. Лист не містить тексту, email відвідувача чи імені автора. Якщо поштовий провайдер не налаштований або відправка не вдалася, **саме звернення зберігається**, але про нього потрібно дізнатися з кабінету. Відвідувачеві email-відповідь **не надсилається**; для нього призначений чат та мітка непрочитаного.

**Обмеження:** до 5 нових діалогів на 24 години для одного акаунту й до 60 повідомлень на 24 години з боку користувача (рекомендовано додаткові правила Cloudflare WAF). У кожному перегляді показано до 200 найновіших повідомлень; довгі діалоги потребуватимуть пагінації. Чати зберігаються до 180 днів після останньої активності; їх також прибирає видалення акаунту. Зберігання повідомлень не залежить від згоди на аналіз запитань Оракулом — **переписка не передається в OpenAI**. Сам чат не витрачає токени ШІ.

**Перевірки після розгортання:**
1. Пройти email-авторизацію й створити діалог із тематичної сторінки; чернетка не має з'явитися на сервері до підтвердження й натискання «Надіслати звернення».
2. Адміністратор бачить новий діалог і читає його; якщо `ADMIN_NOTIFY_EMAIL` налаштовано, перевірити отримання короткого листа.
3. Адміністратор надсилає відповідь; у користувача на сайті з'являється мітка непрочитаного, яка зникає після відкриття діалогу.
4. Під другим зареєстрованим акаунтом `GET /access/chat/thread?id=<first-account-thread>` має повернути 404; гість отримує 403; без токена — 401.
5. Після закриття діалогу користувач не може відповідати; після повторного відкриття — може.
6. Видалення акаунту знищує й належні йому приватні переписки.
7. Відправити 6-й новий діалог протягом доби — очікується 429.
8. Перевірити нову сторінку, відповіді й бейджі на телефоні та комп'ютері.

**Не є завершеним запуском:** усі ці зміни внесено до репозиторію, але Cloudflare Worker, D1, Resend, Turnstile та `ADMIN_NOTIFY_EMAIL` потрібно підключити й розгорнути вручну. Без цього інтерфейс показує, що чат не налаштовано, і не повинен імітувати отримання повідомлень.

## Предметне дослідження тексту та графіки

На відкритих сторінках `model.html`, `feniks.html`, `demo.html` біля змістових розділів автоматично з'являється **«Обговорити з Оракулом»**, якщо для розділу є запис у `assets/context.json`. Посилання відкриває `oracle.html?source=<page>&focus=text:<page>:<section>`. Для графіки, зареєстрованої в `assets/visuals.json` зі стабільним `id` формату `GR-001`, `assets/visuals.js` показує відповідну дію з `focus=graphic:GR-001`.

У діалозі показується назва обраного об'єкта, посилання на публічний матеріал і дія **«Загальний діалог»**. Відвідувач ставить власне запитання; автоматичного витрачання токенів при відкритті теми немає.

Кожний запит передає **лише ідентифікатор** `focus_context`. Новий Worker перевіряє ID та сам завантажує відповідний текстовий фрагмент із `assets/context.json` або паспорт графіки з `assets/visuals.json`. **Візуального аналізу зображень немає**, жодні байти PNG/SVG/WEBP не надсилаються в OpenAI. Модель отримує текстовий контекст у межах встановленого обмеження обсягу. Це спричиняє певні додаткові **текстові токени** на кожне запитання, але не плату за обробку зображення.

Фокус не змінює канонічний корпус епістем і не замінює пошук у ньому. Якщо відвідувач запитує про іншу тему, Оракул може змінити напрям дослідження. Непідтверджені параметри схеми не можна вигадувати. У випадку, коли новий Worker ще не розгорнуто, клієнт після відповіді попереджає, що серверний фокус не був підтверджений.

**Перевірка після розгортання Worker:** відкрити `oracle.html?source=model&focus=text:model:definition`, переконатися у відображенні назви теми, поставити запитання та перевірити, що API повернув `focus_applied:"text:model:definition"`. Окремо перевірити вихід у загальний діалог, переходи між сторінками, інші текстові розділи й паспорт наявного графічного матеріалу (коли він буде доданий).

**Синхронізація:** якщо редагується текст тематичної сторінки, потрібно одночасно оновлювати відповідне поле `content` у `assets/context.json`. Без цього Оракул використовуватиме застарілий фрагмент. Для майбутніх епістем та інших інформаційних об'єктів передбачений той самий принцип ID + паспорт + зв'язки, але окремі сторінки епістем ще не підключені.
